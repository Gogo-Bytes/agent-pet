## 1. 产品一句话

Agent Pet 是一个陪伴用户使用各种 AI Agent 的桌面宠物。它用轻松、可爱的方式表达 Agent 的工作状态，让用户在不学习专业配置的情况下获得陪伴感和反馈。

pi 是第一个接入对象，不是产品边界。后续应能扩展 Codex、Claude Code、Cursor 及其他具备受支持观察能力的 Agent。

## 2. 已确认的产品原则

### 多 Agent 优先

- 产品界面使用通用的 Agent 语言，不把 pi 的术语暴露为主流程。
- 每一种 Agent 通过独立 Adapter 接入，共享统一的发现、连接、Session 和状态表达。
- 首个实现阶段可以只支持 pi，但产品结构不能为 pi 特化到无法扩展。
- 未支持的 Agent 可以显示为即将支持，但不能让用户误以为产品只服务 pi。

### 极低使用门槛

- 默认自动检测和推荐，只有检测失败或存在歧义时才要求用户选择。
- 用户流程应接近“找到 Agent → 允许陪伴 → 完成”，不要求用户理解目录、token、socket、权限位、运行时或协议名称。
- 技术细节、隐私边界和失败证据可以查看，但默认收起，不阻塞主流程。
- 所有失败都要给出下一步可执行的普通语言提示。

连接详情按最新用户反馈直接使用右侧内容区，以普通分节呈现名称、检查、位置和管理操作；不再用居中的大型装饰卡片压缩可用空间。部署预览保留有明确确认目的的局部边界。见 [正式修订证据](CONNECTION-DETAIL-FLAT-ACCEPTANCE.md)。

### 娱乐和陪伴定位

- Agent Pet 首先是开心、轻松、愿意长期打开的桌面宠物，不是工作台、安全审计器或 Agent 管理后台。
- 视觉、文案和动效优先表达宠物的情绪、陪伴和反馈。
- “工作中、完成、出错、离线”等内部状态要转换成用户能直觉理解的宠物状态。
- 管理窗口也应保持宠物产品的语气；技术诊断放入次级详情。

### Electron 外壳，Web 优先验证

- 先在浏览器中验证信息架构、视觉风格和主要交互，再接入 Electron 的真实 IPC 和文件操作。
- Web 原型使用内存 mock bridge，不读取真实配置、不写文件、不启动 Agent。
- 原型应与正式 Renderer 共享可复用的界面模型和组件边界，但原型代码明确标记为 throwaway。
- 设计确认后只把获选方案重写进正式桌面界面，淘汰其他方案。

## 3. 用户心智模型

用户不应该先想“配置桥接”，而应该想：

> “我想让这个小宠物陪我使用哪个 AI？”

产品需要围绕以下问题组织界面：

1. 我的 AI 伙伴有哪些？
2. 哪个伙伴正在工作、等待或完成？
3. 宠物现在是什么状态？
4. 我下一步只需要做什么？

## 4. 产品形态

### 桌宠浮层

- 3D 宠物、气泡和轻量快捷操作。
- 用宠物的表情、动作和气泡表达 Agent 状态。
- 不承载安装向导、复杂配置或技术诊断。

### 管理窗口

- 以“选择 AI 伙伴”和“让宠物陪伴”作为主任务。
- 首次使用采用逐步引导，而不是一页堆叠多个诊断卡片。
- 日常使用显示连接概况、宠物偏好和简单修复入口。
- 宠物和后续环境使用 Three.js 作为可替换的 3D 场景；导航、按钮、状态文字、设置和可访问交互使用 HTML。
- 3D 场景表达空间、角色、情绪和状态，不承担复杂表单或唯一信息来源。

### Agent Provider

- 每种 Agent 是一个可插拔 Provider/Adapter。
- Provider 负责发现、授权连接、Session 观察和可选的打开原窗口能力。
- Provider 的技术差异留在 Main 和诊断详情，不泄漏到默认产品语言。

## 5. 交互方向候选

Web 原型阶段先比较三种结构完全不同的方案：

1. **宠物陪伴首页**：宠物和情绪状态为中心，Agent 伙伴作为轻量选择卡片。
2. **单步连接向导**：一次只做一个动作，完成“找到 → 选择 → 允许 → 陪伴”。
3. **桌面宠物控制中心**：宠物状态为中心，连接和设置从抽屉或弹层进入。

原型默认通过 URL 参数切换，例如 `?variant=a|b|c`，让用户可以直接比较方案。

### 已确认选择

用户已选择 **方案 A：宠物陪伴首页** 作为后续深化基线。它的核心特点是：宠物主视觉、轻松的陪伴文案、Agent 伙伴轻量选择和一个明确的主动作。方案 B、C 暂时保留在 throwaway 原型中用于参考，不进入桌面端实现。

下一轮只深化 A 的状态和流程：首次使用、等待 Agent、工作中、已完成、连接中断、未支持 Agent；不重新引入技术型控制台结构。

## 6. 功能信息架构

方案 A 的桌面首页负责“看全局、做快捷动作”，不承担所有配置细节。正式管理窗口暂定分为四个入口：

### 首页

- 所有在线配置的宠物处于同一场景，同 Provider 不同配置保持独立身份。
- 全景无常驻身份或标签；点击模型或键盘入口聚焦才展示 Agent、宠物名、任务状态与配置名。
- 点击空白、Escape 或返回全景退出；离线/移除后离场并清除失效聚焦。
- 无在线 Agent 有明确空态；连接仅从底部导航进入，首页没有“查看连接”按钮。

### 宠物

- 展示内置和已导入的宠物形象。
- 支持导入符合固定格式的宠物包，而不是任意拖入一个 GLB 就宣称支持。
- 允许为不同 Agent 连接选择不同宠物。
- 保留全局默认宠物；没有单独指定的 Agent 使用默认宠物。
- 导入失败时保留当前形象，不覆盖或删除已有资产。

### 连接

**定位已确认（2026-10-13）：关键配置功能区。** 帮助非技术用户将本机安装的 Agent 接入 Agent Pet，并确认能接收实时状态。这里不展示宠物、不分配形象，交互采用清晰、可信、易恢复的配置流程。视觉仍须达到游戏菜单与娱乐平台的完成度：彩色身份标识、状态图形、精细排版和动作反馈与首页/宠物一致；不等同于普通后台工具。

- 扫描本机当前支持的 Agent，并显示“已找到、未连接、已连接、需要处理”等用户状态。
- 对已识别且支持的 Agent 提供“一键配置”：自动填写类型、名称和可明确匹配的配置位置，直接进入检查与部署确认，不再要求用户重新选择目录或经过手动添加向导。多处程序安装共用一个配置位置时合并为一个配置入口；独立配置仍保持独立身份。必要的具体读取授权、部署预览与确认保留。
- 允许用户在自动扫描失败时手动选择连接文件或目录。
- 不把扫描、授权、连接和运行状态混成一个绿色开关。
- 技术路径、权限和协议详情只在需要排查时展开。

### 设置

- 放置应用级偏好，不放 Agent 专用连接步骤。
- 已确认渲染、软件、宠物、提醒、关于五类；无文字布尔开关、横向分组标题和正文独立滚动。
- 设置页不能为了“看起来完整”而添加没有明确用户价值的开关。

## 7. 宠物资产和 Agent 绑定

宠物形象与 Agent 连接是两个独立对象，通过绑定关系连接：

```text
PetAsset  <- AgentPetBinding ->  ConfiguredAgent
                 \            -> 使用全局默认宠物作为 fallback
```

当前正式版只使用真实内置 starter.glb，收藏、绑定、实际 clip 试播入口已迁移；六只演示宠物及睡觉动作不冒充资产接入。受约束的本地导入包尚未实现，未来方向暂定为一个目录，至少包含：

- 一个 `.glb` 模型文件；
- 一个描述模型名称、版本、作者、许可证和动画映射的 `.json` 文件；
- 后续可加入缩略图和校验元数据，但不能依赖远程资源。

导入前需要检查格式、目录结构、文件大小、纹理/几何/骨骼/动画复杂度和必需的 idle 动画。具体 schema、目录命名和动画 fallback 在宠物资产设计阶段单独确定。

## 8. 连接能力的产品表达

### 已确认的原则

- “连接”是本机 Agent 的接入与管理功能区，使用普通配置语言；此前“找到伙伴 → 宠物开始陪伴”的流程表达已被本轮定位修正。
- 安装被发现、配置完成、Agent 在线、真实工作状态已收到分别表达。不能以“找到了”或“写入完成”冒充接入成功。
- 主流程不要求终端操作、手动编辑配置或猜测文件路径。只在必要时引导用户做一个明确动作。
- 本轮只分析正式版体验与原型结构，不决定各 Agent 的接入协议，也不授权真实扫描、配置修改或部署。

### 当前原型方案（仍待用户验收）

默认页面以已接入配置列表和明确的“一键扫描”入口为主体，辅以手动选择位置。首次使用显示一个简洁扫描空态；不出现雷达或宠物。少量连接使用紧凑信息行，信息量增加时允许列表，不为了延续游戏页强行使用头像矩阵。

新增流程在页面内的连续配置面板展开：

```text
查找本机支持的 Agent → 选择对象 → 确认接入 → 配置与检查 → 完成 / 等待下一步
        └─ 未找到：重新查找 / 指引选择位置
        └─ 多个位置：选择一个，清楚区分名称与来源
```

每个阶段只保留一个主要动作。能自动完成的步骤自动推进，只在选择和必要确认时停下；用户随时知道当前阶段、下一步是否需要自己操作。失败保留前面的选择，在当前步骤重试，不让用户从头开始。

| 用户看到的情况 | 页面提供的下一步 |
| --- | --- |
| 找到，尚未添加 | 添加连接 |
| 已配置，但 Agent 未运行 | 引导打开 Agent，保留配置，等待检查 |
| 需要重启/重新打开才生效 | 显示一句明确指引与再次检查入口；不能假定每个 Agent 都需要此步 |
| 连接正常，尚无工作事件 | 表达已连接/等待状态，不认定失败 |
| 已收到状态 | 用最近状态与时间提供验证证据，不依赖宠物展示 |
| 接入或后续同步异常 | 普通语言说明原因、一个推荐修复动作，详情按需展开 |

配置列表与详情提供：Agent/配置身份、配置位置、配置可用性、刷新检查、更换位置和移除。通信健康和最近工作状态留在首页，不作为配置页字段；配置检查通过不等同于通信在线或工作事件验收。移除范围需解释清楚，不与卸载本机 Agent 混同。连接类型选择与本页详情选择均不改变首页当前 Agent。未支持类型明确标记，不显示可成功接入的操作。

切换页面保留配置流程、选择与结果；正式版本已有连接跨应用重启保存。窄窗口使用自然布局和局部滚动，不采用绝对定位拼接卡片。真实接入的修改预览、授权、保留未知数据和撤回规则继续遵循 MVP 执行计划；界面如何表达这些内容先用演示数据验证。

需随接入能力确认的产品边界：每类 Agent 需要的确认/生效动作、是否支持多个配置位置及命名、验证所能证明的阶段、移除连接需要撤回的改动。界面承载这些差异，主流程不提前承诺全部一键完成。

## 9. 尚未冻结的产品问题

- 多个同类 Agent 配置与名称已确认；当前 pi 已扩展为每配置独立接入，真实 TUI 空闲连接/多 peer/多配置/干净应用重启与撤回已验证，模型任务矩阵仍待验收。
- 同一个 Agent 的多个 Session 是否统一使用该 Agent 的宠物，还是允许按项目覆盖。
- 宠物导入包的正式 JSON schema、动画命名和版本迁移规则。
- 宠物资产是否允许用户删除、恢复默认和导出。
- 硬件 GPU/耗电与系统设置实机覆盖仍需补充；已确认的偏好均有默认、校验、持久化与运行时路径。
- 连接失败时首页显示的最小信息和可执行恢复动作。

## 10. 当前范围与后续范围

## 10.1 3D 场景与 HTML 交互架构

正式桌面界面采用“双层呈现、单一状态源”：

```text
应用状态 / 投影快照
        ├── Three.js 场景：宠物、房间、装饰、动画、空间状态
        └── HTML UI：导航、快捷操作、Agent 状态、设置、导入和错误反馈
```

- Three.js 负责宠物模型、场景布置、镜头、动画和氛围效果。
- HTML 负责主要操作交互，保证键盘、辅助功能、文本缩放和可测试性。
- 两层不各自维护连接、宠物绑定或 Session 状态；它们都订阅同一个 renderer-safe snapshot。
- 3D 场景中的可点击物只提供轻量快捷动作，并必须有 HTML 等价入口。
- 复杂连接流程、宠物包导入、设置表单和失败详情只使用 HTML，不把交互埋进 3D 模型。
- Web 原型首页已采用真实 Three.js/R3F 场景验证多宠物与镜头聚焦；宠物页保留 CSS/HTML 展示及操作原型。正式接入再使用实际宠物资产，HTML 信息与等价操作入口继续保留。

这个方向保留角色展示和轻量状态层的游戏感，同时保持界面简洁，避免把关键操作做成难以访问、难以自动化测试的 3D 热区。

### 当前可复用的实现基础

- Electron + React/R3F 桌宠。
- macOS 本地 `.app` 已有可运行的 arm64 预览包。
- pi 的只读观察、连接、部署预览和选择性撤回已有实现与隔离测试证据。
- 管理窗口已有 bridge 注入边界，可接入浏览器 mock bridge。

### 当前不应被误解为最终产品的部分

- 现有管理窗口是 pi 优先的技术型实现，尚未达到低门槛娱乐产品的体验目标。
- M1–M5 的完成状态只说明本地 pi MVP 的实现证据，不说明多 Agent 产品方向已完成。
- Codex、Claude Code、Cursor 等 Adapter 尚未交付。
- Web 视觉原型已创建，入口见 [桌面原型源码](../apps/desktop/prototype/main.tsx)；方案 A 已选定，尚未进入正式 Renderer。

### 阶段顺序

1. 统一产品方向和领域语言（本文及 `CONTEXT.md`）。
2. ~~创建浏览器 UI 原型，比较三种结构和风格。~~（已完成）
3. **深化方案 A 的状态、文案和首次使用流程。**
4. 形成正式管理窗口的信息架构和视觉规范。
5. 将选定设计接入 Electron Renderer，保留真实 Main/preload 安全边界。
6. 将 pi 适配到通用 Provider 结构。
7. 再按同一 Provider 契约扩展其他 Agent。

## 11. 明确不做的事情

- 不把产品做成专业 Agent 运维控制台。
- 不让用户复制 token、编辑配置文件或执行终端命令完成日常接入。
- 不把技术实现细节放在首次使用的主流程中。
- 不在没有真实 Adapter 能力和验收证据时虚构“支持”某个 Agent。
- 不因为先做 Web 原型而绕过 Electron 的权限、IPC 和真实文件写入边界。

## 12. 宠物页与共享场景（2026-10-13）
