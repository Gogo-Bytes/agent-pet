## 1. 可以确认的方向

1. **正常 pi 用户配置存在零 settings 修改路径**：0.85.1 自动发现用户 extensions 下的独立文件，可采用产品专属单文件。无需 pi install、shell 配置或运行时 npm 安装。
2. **并非所有配置都可自动接入**：extensions 根入口/manifest、ignore、排除规则、--no-extensions、自定义 agentDir 均可能影响加载。不得悄悄绕过用户禁用意图。
3. **无需环境变量的桥接有平台 API 基础**：私有发现记录 + Unix socket + 扩展每次重连重新发现；具体路径、身份认证及权限保证仍需验证。
4. **安装与加载分离**：写文件只能证明已配置；认证连接才能证明组件在线；真实工作→终态才能证明观测链路，三者单独记录。
5. **不支持热注入**：TUI 在 streaming/compacting 时拒绝 /reload。仅提示用户空闲时重载或正常重新打开，绝不自动操作。
6. **复制的扩展不依赖 App 安装位置**：自包含文件只用 Node builtins，不要求外部 Node 理解 Electron ASAR；升级不修改已签名 bundle。
7. **安装包是独立交付**：electron-vite build 不是用户可安装产品。macOS 面向普通用户的分发还需签名、公证、干净机器与升级/卸载验收，不要求用户关闭 Gatekeeper。

## 2. 推荐的最小产品契约（待实现）

### 目标与发现

- 首个认证对象限定标准发行版 pi TUI，0.85.1 是当前静态核实基线，不代表所有版本均支持。
- 分离 Agent 安装候选与配置目标。同一安装可能使用多个 agentDir，多个安装也可能共享目标；按规范化配置目标防止重复部署，不按可执行文件数量复制扩展。
- 默认用户目录只作候选；GUI 不运行 Agent、不执行登录 shell、不遍历会话来推测真实配置。允许用户图形化选定配置目录；握手前不声称这个目录就是活跃进程的实际目标。
- 初版 root-entry、ignore 或用户禁用规则冲突时清楚说明原因，不自动改 index/settings/trust。若以后要提供最小共享配置修改，必须独立设计并重新取得授权。

### 安装与撤销

- 授权预览展示范围、数据字段、文件变更、生效条件和撤销方法。产品专属名称暂定 `agent-pet.ts`，遇同名未知内容停止，不覆盖。
- 私有目录保存版本、目标标识、所有权及内容摘要；暂存/备份不使用可被自动发现的 `.ts/.js` 副本，避免双加载。
- 安装/升级采用原子发布与并发变更检查；部分失败仅撤回本次自有变更，不恢复整份旧 settings。
- 断开先持久化撤销并关闭该目标既有连接、拒绝后续排队消息，再删除仍匹配所有权的自有文件。清理失败不撤销“拒绝接入”状态。
- 直接拖删 App 不能保证清理扩展。扩展残留必须惰性、非阻塞、有界重试且不保活；重装发现残留后先向用户确认，不自动恢复已撤销授权。

### 运行连接

- 在单实例锁和 listener 就绪、权限校验成功后发布发现记录；记录带 schema/protocol、instance/generation、endpoint、非秘密凭证引用。
- 秘密不写 renderer、argv、日志、发现记录或导出诊断。认证成功前不发送 Session 名称/项目名；hello/ack 协商版本与能力。
- 按目标管理授权和撤销；按连接区分在线 Session，不能用单个 socket 的 close 将整个 Agent 标记离线。
- 认证超时、连接数/速率/帧大小限制、退避与 shutdown 幂等清理必须有明确测试。空闲无业务事件不等于失联。
- Pet 重启只恢复当前 working/idle，不补发离线历史 unread。配置目标、pi 逻辑 session、扩展运行实例与 Pet 服务实例分别建模。
- pi reload 保留逻辑 session UUID，但重建扩展 runtime；目前扩展模块生成随机 processInstanceId。后续须明确并测试 reload 的 UI 身份行为，不能根据 UUID 保持就宣称现有合成 Session ID 保持。

## 3. 安全方案建议与未决项

### 建议首版威胁边界

建议以“同一 macOS 用户下明确授权的本机观察”为边界：防其它 OS 用户读取/连接、防误配置、防 Renderer 越权；不承诺隔离 root 或同 uid 的恶意代码。pi 扩展本身拥有宿主权限。

在这个边界内，建议优先评估**每目标独立随机秘密、私有文件权限保护**，而不是为了表面上的 Keychain 标签先引入 native helper。它是明文 at rest，必须明确风险并经过评审，不是已选定方案。Keychain/helper 若要真正增强应用级隔离，必须回答外部通用 Node 如何取钥且不把任意同用户进程都放行，不能直接复用 Electron safeStorage ciphertext。

### 当前推荐：私有本机 UDS，不要求连接证书

经用户提醒重新审视复杂度后，当前推荐改为 **用户私有目录 + UDS + 每目标随机 token**，见 [本机安全边界与简化建议](P0-LOCAL-SECURITY-DECISION.md)。以其它 OS 用户隔离、防误配与可撤销授权为目标，不承诺抵御同 uid 恶意代码；ack 不是双向密码学认证。该取舍仍待整体技术评审及权限验证，不因简化而放宽路径/权限要求，不回退到 TCP。

以下是历史候选与实验记录，不再作为首版必选路线：

首轮隔离实验见 [P0-ISOLATED-VALIDATION.md](P0-ISOLATED-VALIDATION.md)：当前 Electron 36.9.5 拒绝候选 PSK 套件，且 getCiphers 的 PSK 项为空，排除作为当前默认方案。证书 TLS + 加密通道目标凭证在系统 Node/Electron 两方向、TLS1.2/1.3 下通过有界互通；但这只证明传输可行，不证明产品必须采用 TLS。信任锚/生成/更新/到期/撤销持久化当时尚未验证，当前不再作为首版本机路线的必选工作。

以下保留初始比较背景，不代表 PSK 仍是当前推荐：成熟候选原为 TLS-PSK over UDS，或固定信任锚的 server TLS + 按目标 bearer。前者避免证书发行但需验证 Electron/pi OpenSSL 与 PSK 套件互通；后者有证书发行、固定信任和轮换成本。两者都不能仅凭文档判定可用，不自创 challenge-response 密码协议。

仅增加明文 token + ack 不构成双向认证。TLS 恢复会话也必须受撤销 epoch 约束，不能让旧连接或 tickets 绕过撤销。若不能满足约定边界，明确失败，不静默退回无认证 TCP/宽松文件权限。

### 路径尚不冻结

稳定 bootstrap 命名与用户目录解析需双方一致；socket 采用短、私有、实例独占路径。macOS UDS 典型上限是字节而不是字符，不能直接在深层 userData 下任意拼路径。

不能仅用 `O_NOFOLLOW` 宣称防住全部父目录替换；私有父目录、fd 验证、owner/mode/ACL、独占创建与有界大小需一起验证。不可信自定义目录首版可拒绝，不为泛化牺牲安全。

## 4. P0 剩余验证清单与结束条件

下表为完整有界验证计划。已完成传输的部分互通/拒绝/撤销场景、10 项文件基础检查和实际 pi resolver 的 11 项发现检查。后者证明 ignore 移除候选，而 settings 排除保留 enabled:false；两份相同 `.ts` 不同路径仍有两个 enabled 候选。没有执行扩展、加载器后续过滤或真实用户配置；未覆盖项保持待验证：

| 验证 | 环境约束 | 通过证据 |
| --- | --- | --- |
| 最小安装/发现 | 临时配置目录、合成文件；不使用用户真实 pi 目标 | 普通目录可发现；root entry/ignore/禁用/冲突明确拒绝；备份不双加载 |
| 传输互通 | 独立临时私有 socket 与合成凭证；不用用户端点 | Node/Electron 的新 UDS 路线握手、拒绝错误秘密/实例、撤销与重连；准确记录版本；不称为双向密码学认证 |
| 文件/权限 | 私有临时目录；真正跨用户测试需另行授权环境 | 长/Unicode 路径、symlink、宽权限、并发替换、残留 socket，不泄漏或误删；mode 检查不替代 ACL 证明 |
| 生命周期 | 合成连接；如需 pi 运行测试，只能专用测试实例并明确授权 | 重启重新发现、撤销既有连接/排队消息、安装/更新中断恢复 |
| 发布边界 | 不读取用户 Keychain/证书 | 冻结包标识、目标 macOS/CPU 架构、打包工具及签名条件；证书与分发账号由用户另行授权 |

这些验证不是生产功能开发；若允许执行，将放独立临时测试环境，结束清理合成材料，不接触真实配置。完成后再冻结具体协议/目录/安装事务，审阅通过后进入 P1/P2。

## 5. 当前结论

**产品方向可行，pi 默认配置的一键接入有官方基础及有界动态发现证据；方案已可交整体设计评审。** 不应将“研究完成”报成安装器、安全与发布验收全部通过。

建议评审确认后进入 P1 管理窗口基础（不写真实 Agent 目标）；P2 实际接入写入前需落实发布原语、路径权限、持久撤销与失败注入。跨用户 ACL、完整 runtime/reload 和发布签名等门槛应绑定对应阶段，不通过无限延长 P0 假装提前完成整个产品。未获用户实施确认前仍不启动 P1。

用户已允许继续隔离验证，但不等同正式批准凭证明文存储的最终安全设计。下一步按简化建议验证私有 UDS 访问控制、目标授权与安装事务，再核实剩余门槛；不继续把证书生命周期作为首版前置要求。无需用户选择 TLS cipher 或手填路径，具体技术选择应由验证证据收敛。
