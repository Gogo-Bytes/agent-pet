# Agent Pet 产品方向与统一路线

> 本文是当前产品定位、交互原则和阶段边界的统一入口。实现细节与验收证据分别见 [MVP 执行计划](MVP-EXECUTION-PLAN.md)；领域词汇见 [CONTEXT.md](../CONTEXT.md)。如果旧文档与本文冲突，以本文的产品方向为准，以 MVP 执行计划的证据为准。

更新时间：2026-10-10

当前进度：**Web 原型阶段，方案 A 已由用户选定为视觉基调；尚未接入桌面端。**

## 1. 产品一句话

Agent Pet 是一个陪伴用户使用各种 AI Agent 的桌面宠物。它用轻松、可爱的方式表达 Agent 的工作状态，让用户在不学习专业配置的情况下获得陪伴感和反馈。

pi 是第一个接入对象，不是产品边界。后续应能扩展 Codex、Claude Code、Cursor 及其他具备受支持观察能力的 Agent。

## 2. 已确认的产品原则

### 多 Agent 优先

- 产品界面使用通用的 Agent 语言，不把 pi 的术语暴露为主流程。
- 每一种 Agent 通过独立 Adapter 接入，共享统一的发现、连接、Session 和状态表达。
- 首个实现阶段可以只支持 pi，但产品结构不能为 pi 特化到无法扩展。
- 未支持的 Agent 可以显示为即将支持，但不能让用户误以为产品只服务 pi。

### 极低使用门槛

- 默认自动检测和推荐，只有检测失败或存在歧义时才要求用户选择。
- 用户流程应接近“找到 Agent → 允许陪伴 → 完成”，不要求用户理解目录、token、socket、权限位、运行时或协议名称。
- 技术细节、隐私边界和失败证据可以查看，但默认收起，不阻塞主流程。
- 所有失败都要给出下一步可执行的普通语言提示。

### 娱乐和陪伴定位

- Agent Pet 首先是开心、轻松、愿意长期打开的桌面宠物，不是工作台、安全审计器或 Agent 管理后台。
- 视觉、文案和动效优先表达宠物的情绪、陪伴和反馈。
- “工作中、完成、出错、离线”等内部状态要转换成用户能直觉理解的宠物状态。
- 管理窗口也应保持宠物产品的语气；技术诊断放入次级详情。

### Electron 外壳，Web 优先验证

- 先在浏览器中验证信息架构、视觉风格和主要交互，再接入 Electron 的真实 IPC 和文件操作。
- Web 原型使用内存 mock bridge，不读取真实配置、不写文件、不启动 Agent。
- 原型应与正式 Renderer 共享可复用的界面模型和组件边界，但原型代码明确标记为 throwaway。
- 设计确认后只把获选方案重写进正式桌面界面，淘汰其他方案。

## 3. 用户心智模型

用户不应该先想“配置桥接”，而应该想：

> “我想让这个小宠物陪我使用哪个 AI？”

产品需要围绕以下问题组织界面：

1. 我的 AI 伙伴有哪些？
2. 哪个伙伴正在工作、等待或完成？
3. 宠物现在是什么状态？
4. 我下一步只需要做什么？

## 4. 产品形态

### 桌宠浮层

- 3D 宠物、气泡和轻量快捷操作。
- 用宠物的表情、动作和气泡表达 Agent 状态。
- 不承载安装向导、复杂配置或技术诊断。

### 管理窗口

- 以“选择 AI 伙伴”和“让宠物陪伴”作为主任务。
- 首次使用采用逐步引导，而不是一页堆叠多个诊断卡片。
- 日常使用显示连接概况、宠物偏好和简单修复入口。

### Agent Provider

- 每种 Agent 是一个可插拔 Provider/Adapter。
- Provider 负责发现、授权连接、Session 观察和可选的打开原窗口能力。
- Provider 的技术差异留在 Main 和诊断详情，不泄漏到默认产品语言。

## 5. 交互方向候选

Web 原型阶段先比较三种结构完全不同的方案：

1. **宠物陪伴首页**：宠物和情绪状态为中心，Agent 伙伴作为轻量选择卡片。
2. **单步连接向导**：一次只做一个动作，完成“找到 → 选择 → 允许 → 陪伴”。
3. **桌面宠物控制中心**：宠物状态为中心，连接和设置从抽屉或弹层进入。

原型默认通过 URL 参数切换，例如 `?variant=a|b|c`，让用户可以直接比较方案。

### 已确认选择

用户已选择 **方案 A：宠物陪伴首页** 作为后续深化基线。它的核心特点是：宠物主视觉、轻松的陪伴文案、Agent 伙伴轻量选择和一个明确的主动作。方案 B、C 暂时保留在 throwaway 原型中用于参考，不进入桌面端实现。

下一轮只深化 A 的状态和流程：首次使用、等待 Agent、工作中、已完成、连接中断、未支持 Agent；不重新引入技术型控制台结构。

## 6. 当前范围与后续范围

### 当前可复用的实现基础

- Electron + React/R3F 桌宠。
- macOS 本地 `.app` 已有可运行的 arm64 预览包。
- pi 的只读观察、连接、部署预览和选择性撤回已有实现与隔离测试证据。
- 管理窗口已有 bridge 注入边界，可接入浏览器 mock bridge。

### 当前不应被误解为最终产品的部分

- 现有管理窗口是 pi 优先的技术型实现，尚未达到低门槛娱乐产品的体验目标。
- M1–M5 的完成状态只说明本地 pi MVP 的实现证据，不说明多 Agent 产品方向已完成。
- Codex、Claude Code、Cursor 等 Adapter 尚未交付。
- Web 视觉原型已创建，入口见 [桌面原型源码](../apps/desktop/prototype/main.tsx)；方案 A 已选定，尚未进入正式 Renderer。

### 阶段顺序

1. 统一产品方向和领域语言（本文及 `CONTEXT.md`）。
2. ~~创建浏览器 UI 原型，比较三种结构和风格。~~（已完成）
3. **深化方案 A 的状态、文案和首次使用流程。**
4. 形成正式管理窗口的信息架构和视觉规范。
5. 将选定设计接入 Electron Renderer，保留真实 Main/preload 安全边界。
6. 将 pi 适配到通用 Provider 结构。
7. 再按同一 Provider 契约扩展其他 Agent。

## 7. 明确不做的事情

- 不把产品做成专业 Agent 运维控制台。
- 不让用户复制 token、编辑配置文件或执行终端命令完成日常接入。
- 不把技术实现细节放在首次使用的主流程中。
- 不在没有真实 Adapter 能力和验收证据时虚构“支持”某个 Agent。
- 不因为先做 Web 原型而绕过 Electron 的权限、IPC 和真实文件写入边界。
